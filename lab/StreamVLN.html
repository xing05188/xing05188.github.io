00 / THE SHORT VERSION先用三分钟，建立整体印象

如果只记一句话：StreamVLN 是一个让机器人「看着连续的摄像头画面、听着人的一句话指令、实时决定下一步往哪走」的模型框架。

它属于一个叫 视觉语言导航（Vision-and-Language Navigation，简称 VLN）的研究方向。这个方向要解决的事情，说白了就是： 你对着一台机器人说「走进厨房，绕过餐桌，在冰箱前停下」，它得自己看懂画面、找到路、走过去。

这件事听起来像扫地机器人，但难度完全不同。扫地机器人是在一张已知地图上撞来撞去；而 VLN 要求机器人理解一句它从没听过的话，并且在从没来过的房子里把这句话变成一连串正确的动作。

PROBLEM 01
看得要细

画面里的门、台阶、沙发扶手，任何一个细节都可能决定该不该往前。

PROBLEM 02
记得要久

走了三分钟，得记得「我已经经过厨房了」，否则会原地打转。

PROBLEM 03
反应要快

真实机器人不能想 5 秒才走一步，人会撞上来，控制也会抖。

这三件事互相打架。想看得细，就要多保留画面细节，计算量大；想记得久，就要把很长的历史都塞进模型，更慢；想反应快，就只能看最近几帧，于是「失忆」。 过去的方法基本都在这个三角里做取舍，牺牲一个换另外两个。

StreamVLN 的答案

它把「记忆」拆成两条通道，像人走路时的大脑一样分工：

快通道——只保留最近一小段「看到什么 → 做了什么」的对话，用 KV 缓存复用让每一步几乎不用重算，保证反应快。

慢通道——把更早的画面压成一份「空间记忆」，用 3D 体素剪枝把重复的画面扔掉，只留每个空间位置上最新的那一小块，保证不乱、不爆内存。

两条通道合起来，模型就能在上下文长度有上限、算力有上限的前提下，一直走下去。

成绩上，它在两个公开测试集 R2R-CE 和 RxR-CE 上拿到了「只用 RGB 摄像头」这一类方法里的最好结果；在真机（宇树 Go2 机器狗）上，0.27 秒就能吐出 4 个动作，够实时用了。

读法建议 如果你时间很少：读 00、03、06 三节就能明白它「是什么、怎么想的、怎么动的」。 想彻底搞懂：按顺序读，第 04、05 节是技术核心，第 08 节教你怎么看论文里的表格。

01 / THE TASK这个任务到底是什么

1.1 一个具体场景，走一遍

想象你被蒙上眼睛放进一栋陌生的房子，只给你一句话：「从客厅出发，经过走廊，在第二个卧室的床边停下。」然后有人扶着你往前走，每走一步告诉你「现在你看到的是……」。

你要做的事，就是不断重复一个循环：

看一眼现在的画面 → 回想一下刚才走过哪 → 对照那句话 → 决定下一小步是往前、左转、右转，还是停下。

1.2 三个角色：指令、观察、动作

任何 VLN 系统，输入输出都能归结成三样东西。记住这三个词，后面就不会迷路：

指令 / Instruction
一句人写的自然语言，比如「走过沙发，然后在挂画的墙前左转」。通常 20 到 100 个词。
观察 / Observation
机器人当前看到的画面。真实机器人是摄像头连续视频；仿真里是一帧帧 RGB 图像（有时还带深度图）。
动作 / Action
下一步做什么。连续环境里通常是「前进 25 厘米 / 左转 15 度 / 右转 15 度 / 停止」这类底层指令。

模型的全部工作，就是学会一个函数：动作 = f(指令, 观察历史)。听起来简单，但「历史」这两个字，就是整篇论文的战场。

1.3 为什么会有「连续环境」这个说法

早期的 VLN 研究（2018 年的 R2R 数据集）是在一个「离散」环境里做的：房子被抽象成一张由节点组成的图，机器人不是一个真的在走的东西，而是一个瞬移的观察者——它站在一个节点上，环顾四周，然后选择「跳到」相邻的某个节点。

这样做的好处是简单：动作空间只有「跳去哪个点」，不用考虑碰撞、不用考虑转几度。但坏处也很明显：真实机器人不会瞬移。

2020 年，研究者提出了 VLN-CE（Continuous Environments），把 R2R 那套指令搬到连续环境里：机器人用第一人称视角的 RGB-D 相机，只能输出底层动作，还要处理碰撞、卡住、走歪。StreamVLN 全程都在 VLN-CE 设定下评测，这是它「能上真机」的前提。

1.4 评判标准：什么叫「走对了」

导航任务不像考试有标准答案，得有一套量化指标。论文里会反复出现这五个缩写，先混个眼熟，第 08 节会详细讲怎么读：

指标含义方向
NENavigation Error，终点离目标还有多少米越低越好
OSOracle Success，路上有没有「路过」目标 3 米内越高越好
SRSuccess Rate，最终有没有停在目标 3 米内越高越好
SPLSuccess weighted by Path Length，成功且没绕远路越高越好
nDTW整条轨迹和标准答案轨迹贴不贴合越高越好

最重要的一般是 SR 和 SPL。SR 是「到没到」，SPL 是「到得干不干脆」——一个绕了整栋楼才到终点的机器人，SR 是满分，SPL 会很低。

02 / THE PROBLEM为什么非要「流式」不可

在 StreamVLN 之前，用大模型做导航已经有不错的方案了（比如 NaVid、NaVILA）。但它们都卡在同一个地方：大模型的上下文是有成本的，而导航的视频流是无限的。

2.1 先理解「token」这件事

大模型看不懂图像，它只认识数字序列。所以图像要先被切成小块（patch），每块变成一个 token——可以理解成「一个字」。一帧普通分辨率的画面，通常会被切成 196 个 token 左右。

现在算一笔账。假设机器人每秒走 2 步，走 5 分钟：

项目数量说明
步数6005 分钟 × 2 步/秒
每步画面 token196一帧图像的 patch 数
累计视觉 token≈ 117,600600 × 196
对应显存（KV 缓存）数十 GB论文提到 2K token 约 5 GB，且随长度线性涨

按论文给出的量级估算：上下文越长，KV 缓存占的显存越多，而显存是硬上限。

这就是第一个死结：你不可能把整段视频都喂给模型。

2.2 第二个死结：每一步都在重复劳动

大模型生成回答分两个阶段：先把输入的整段话「读一遍」并算好中间状态（叫 prefill，预填充），再一个字一个字往外吐（叫 decode，解码）。

早期做法是：每走一步，就把「指令 + 之前所有帧 + 之前所有动作」重新拼成一个超长输入，从头 prefill 一遍。第 10 步要读 10 帧，第 100 步要读 100 帧——越走越慢。

2.3 第三个死结：只留最近几帧，就等于失忆

最省事的办法是「只喂最近一帧」。快是快了，但模型不知道自己是刚从客厅进来的，还是已经在这条走廊里转了两圈。它会反复走回头路，或者在岔路口犹豫不决。

论文里有个很说明问题的消融实验：把历史全扔掉（只看当前帧），R2R 上的成功率明显下降；但把历史全部留下，性能反而不如「留一个恰当的窗口」——因为太长的上下文会引入噪声和偏差，模型被无关的旧画面带跑。

关键洞察 导航需要的记忆不是「越多越好」，而是「近的细节 + 远的梗概」。 这恰好是人类走路时的记忆方式：你清楚记得刚才三步脚下有没有台阶，但十分钟前路过的那个房间，你只记得「好像有张桌子」。

2.4 已有做法的三种妥协

做法怎么省代价
抽帧每秒只取 1 帧，或每隔几帧取一帧可能刚好错过「该转弯的那个路口」
压缩特征把图像 token 做池化、或用 Q-Former 压成少量向量改变了模型预训练时习惯的输入分布，精度掉得厉害
每步刷新只输入当前帧，历史靠模型自己「悟」没有真正的记忆，长任务里会绕圈

StreamVLN 的出发点就是：这三条路都不够好，得换一种组织记忆的方式。

03 / THE IDEA核心思想：给记忆修两条车道

StreamVLN 的全部创新，可以浓缩成一个类比：人走陌生大楼时，用的是两种记忆。

第一种是工作记忆。你清楚记得刚才这三五步：左手边有个消防栓，前面地砖有个坑，刚才是从一扇玻璃门进来的。这些信息非常具体、非常新鲜，但只能维持很短时间。

第二种是情景记忆。走了十分钟后，你记不清每一步踩在哪里了，但你记得「我已经穿过大厅了」「厨房在身后」「这层楼我绕了一圈」。这些信息很模糊，但跨度极长，而且足够支撑决策。

人类不会把过去十分钟的每一帧画面都重新在脑子里渲染一遍。我们做的是不断把工作记忆「沉淀」成情景记忆。StreamVLN 干的正是这件事，只不过用工程手段实现：

通道对应机制它负责什么更新频率
快通道
Fast-streaming		 滑动窗口 KV 缓存 最近若干轮「看到什么 → 做了什么」，分辨率最高，用于即时反应 每一步都在变
慢通道
Slow-updating		 3D 体素 token 剪枝 更早的历史画面，去掉重复、只留空间上新信息，用于不迷路 每走完一段才更新

3.1 为什么这样设计是聪明的

注意一个细节：StreamVLN 没有改模型架构。它用的还是现成的 LLaVA-Video（一个能看视频的大模型），只是改了「喂什么、怎么喂、什么时候扔」。

这点很重要。改架构意味着要重新预训练，成本极高、风险极大；而改输入组织方式，可以直接站在一个已经「看得懂画面」的模型肩膀上，只教它「怎么用记忆」。

所以整篇论文的技术贡献可以归成三句话：

  • 快：把「多轮对话」组织成流式序列，靠 KV 缓存复用，让第 100 步和第 2 步一样快。
  • 省：把历史画面按 3D 空间去重，重复看到的东西不重复存。
  • 稳：两阶段训练 + DAgger 纠错数据，让模型学会在走错之后自己拉回来。

04 / FAST LANE快通道：把每一步都「接」在上一步后面

4.1 先搞懂 KV 缓存，只要一个比喻

大模型每读一个 token，内部都要为它算两份「笔记」：一份叫 Key，一份叫 Value。之后每生成一个新 token，都要拿它去和前面所有 token 的 Key 比对、再把对应的 Value 加权求和。

问题来了：如果每走一步都把整段历史重新读一遍，那前面那些 token 的 Key/Value 就要反复重算。而它们的值其实不会变。

KV 缓存就是把这堆笔记留在桌上。下次要用，直接翻，不用重算。这就是为什么你和 ChatGPT 连续聊十轮，第十轮不会明显变慢——前九轮的计算结果一直存着。

一句话 KV 缓存 = 模型读过的内容的「中间计算结果存档」。复用它可以跳过 prefill，只做 decode。 论文里说，这一步能省掉 99% 以上的预填充时间。

4.2 把导航写成一串「对话」

StreamVLN 最关键的一步抽象，是把导航过程写成一个不断变长的对话：

o₁ a₁ o₂ a₂ o₃ a₃ …

其中 o 是观察（observation，一帧画面的 token），a 是动作（action，模型生成的几个字符）。第一轮输入是指令 + o₁，模型输出 a₁；第二轮接着输入 o₂，模型输出 a₂……

因为 a₁ 已经在上一轮生成完了，它的 KV 也已经在缓存里，所以第二轮只需要 prefill 新来的 o₂ 这一帧。这就是流式的本质：永远只处理增量。

4.3 窗口满了怎么办：三步走

缓存不能无限长，所以要有一个滑动窗口。窗口大小 W 轮，永远只保留最近 W 组「观察 + 动作」：

Wj = [ oi−N+1 ai−N+1 … oi ai ]

当窗口装不下新的一轮时，触发一次「交接」：

  1. 把最旧的一段 KV 状态卸载出去 不是删掉，而是从显存里挪走，腾出空间给新帧。
  2. 扔掉「非观察」的 token 指令提示词、模型自己生成的动作用字，这些对后续决策价值低，直接丢弃。
  3. 把这一窗里的观察 token 压缩成记忆 token 交给慢通道，压成 M₀…Mⱼ 这样几个「记忆单元」，挂到下一窗口的输入里。

这一套下来，上下文规模被钉死在一个常数上：不管走 10 步还是 1000 步，模型看到的量都差不多。延迟稳定，显存也可控。

4.4 论文没写、但代码里能看到的真实参数

论文正文对窗口大小给的是符号 N，消融里提到 8。我去看了官方开源实现，几个具体数字值得记下来，因为它们解释了「实际跑起来是什么感觉」：

参数（代码中的名字）默认值含义
num_frames32一个「片段」的长度。每走 32 步，KV 上下文整体重建一次
num_history8记忆里保留的历史帧数（从走过的轨迹里均匀抽 8 帧）
num_future_steps4一次推理输出 4 个动作，而不是 1 个
动作粒度25 cm / 15°前进 25 厘米，左转或右转 15 度，或 STOP

来源：streamvln/streamvln_agent.py 的默认参数与 prompt 定义。

这里有个容易被忽略的工程细节：不是每一步都跑模型。代码里每 4 步才真正调用一次 generate()，中间三步直接消费上一次吐出的动作序列。这相当于「一次想好四小步」，既省算力，又让动作更连贯——不会出现「前进、前进、突然左转」这种抖动。

读论文 vs 读代码 论文讲的是「无限长的流、有界的上下文」；开源实现里，这个「无限」被切成了 32 步一段，段与段之间靠 8 帧记忆衔接，段末会重置一次上下文。 这不是矛盾，而是把理论上的滑动窗口落成了一个可复现的工程近似。写论文看机制，跑代码看参数。

05 / SLOW LANE慢通道：把「看过的地方」去重

5.1 一个反直觉的事实：视频里大部分画面是重复的

机器人往前走了五步，摄像头拍到的五帧画面，其实七八成是同一面墙、同一块地板，只是变大了、偏移了一点。如果每一帧都原样存 196 个 token，相当于把同一面墙存了五遍。

这跟人看视频不一样。人不会记住五张几乎一样的照片，人会记住「那面墙上有一幅画」。也就是说，冗余发生在三维空间里，而不是在时间轴上。

这句话是理解第 5 节的钥匙。已有的压缩方法（抽帧、池化）都在时间轴或特征维度上做文章，而 StreamVLN 选择在三维空间里做去重。

5.2 体素：把空间切成乐高格子

体素（voxel）就是三维的像素。想象把整个房间放进一个巨大的乐高底板，用固定大小的透明小方块把空间填满，每个小方块就是一个体素。

有了体素，判断「这两个画面是不是在拍同一个东西」就变得非常简单：只要它们对应的图像小块落在同一个体素里，就认为是同一个物体。

怎么知道落在哪？靠两样东西：深度图（知道这个像素离我多远）和相机位姿（知道我站在哪、朝哪看）。有了它们，就能把每个图像小块「反投影」回三维空间，找到它属于哪个格子。

5.3 算法其实只有四步

论文里的 Algorithm 1 看着公式多，拆开就是四句人话：

  1. 给每个图像小块算一个「门牌号」 用深度和相机位姿，把第 t 帧第 (x, y) 个小块反投影到 3D，落到哪个体素，门牌号就是几。没有深度的（比如天空）记 −1，直接跳过。
  2. 同一段时间里，同一个格子只留最新的 把时间切成若干段，每段长度 K。段内同一个体素被多次看到，只保留最后那一次——因为最新的视角通常最完整、最清楚。
  3. 整帧太「空」就整帧扔掉 如果一帧里保留下来的 token 比例低于阈值 θ，说明这帧的画面基本都跟别人重复了，干脆整帧不要。论文没公开 θ 的具体取值。
  4. 把保留下来的 token 拼成记忆 这些 token 的向量原封不动，只是数量少了。它们被打包成记忆单元，挂到快窗口前面。

5.4 为什么「挑 token」比「改 token」高明

这是整篇论文里我最欣赏的一个取舍。

常见的压缩方法是改：把 196 个 token 做平均池化变成 49 个，或者用一个小网络把它们重新编码成 8 个向量。问题是，大模型是在「196 个原始图像 token」这种分布上预训练出来的，你突然喂给它一批被改造过的向量，它没见过，理解能力就崩了。

StreamVLN 的做法是挑：我不改任何一个 token 的样子，我只是不给你那些重复的。模型收到的仍然是原汁原味的图像特征，只是数量少了。

效果 论文的消融显示：只对 8 帧记忆做剪枝，R2R 上记忆 token 数量减少 28%，RxR 减少 22%，而成功率基本不掉，R2R 甚至略有上升。 如果把流式帧的 KV 也一起剪（Prune-All），token 能再降 30% 左右，但性能会掉一点点——所以官方默认只剪记忆。

5.5 一个必须说明的落差

开源代码里有一行注释很诚实：

Currently the model does not use voxel pooling. So we only use the rgb.

意思是：公开的推理代码并没有启用体素池化，历史帧是靠「从走过的轨迹里均匀抽 8 帧」来近似的。深度和位姿的输入通道还留着，但实际没参与剪枝。

这带来两个现实影响。第一，你在自己机器上跑，拿到的不是一个「带 3D 去重」的完整系统，而是一个「8 帧均匀采样」的版本，效果会比论文里略打折。第二，如果你想复现论文的剪枝收益，需要自己在数据预处理阶段把体素索引算好——这也是为什么论文强调这套方法依赖深度和相机位姿。

给小白的一句话 论文的「慢记忆」有两个层次：机制层是「压缩历史视觉状态」，实现层是「3D 体素去重」。 前者是必须的，后者是当前最优解；开源版用的是更简单的均匀采样，属于工程上的降级。

06 / ACTION它到底怎么「迈出一步」

6.1 动作空间：只有四个选项

连续环境里，机器人不能「跳」，只能一小步一小步挪。StreamVLN 用的动作集非常朴素，就四个：

字符动作物理含义
↑MOVE FORWARD沿当前朝向前进 25 厘米
←TURN LEFT原地左转 15 度
→TURN RIGHT原地右转 15 度
STOPSTOP停在原地，表示任务结束

25 厘米和 15 度这两个数字不是随便定的，它们来自 VLN-CE 的标准设定。走完一条 10 米的指令路线，大概需要 40 次前进加上若干次转向——所以一次任务里模型要决策上百次。

6.2 一个特别的设计：动作是「写」出来的，不是「分类」出来的

传统导航模型会在最后一层接一个分类头，输出「四个动作各自的概率」，选最大的那个。StreamVLN 不这么干，它让大模型直接把动作当成文字写出来：

↑ ↑ ← ↑

然后外面用正则表达式把这串符号解析成动作序号，交给机器人执行。为什么要绕这一圈？三个好处：

  • 不用改模型结构。任何语言模型都会「接着说」，天生就能输出这串符号，不需要额外训练一个分类头。
  • 一次能输出一串。分类头一次只能给一个动作；文本可以一直写，写到模型觉得够了为止。
  • 保留了模型的推理能力。同一个模型既能输出动作，也能回答「你右边墙上是什么」——论文里专门测了它在 ScanQA 上的视觉问答成绩，没有被导航训练「练傻」。

代价是：模型可能写出格式不对的东西（比如多说了一句解释），所以代码里有个兜底——解析不出动作，就当 STOP 处理。

6.3 一次想四步，是个很实用的 trick

代码默认 num_future_steps = 4：模型一次生成 4 个动作，然后机器人连着执行 4 步，执行完再问模型「现在该怎么办」。

这叫 动作分块（action chunking）。它的好处不只是省算力（推理次数直接降到四分之一），更重要的是动作更连贯。如果每 25 厘米就问一次模型，模型每次都可能因为画面的一点抖动而改变主意，走起来就会「一顿一顿」；一次想四步，天然带一点惯性。

6.4 把一轮完整流程走一遍

下面这张表，是一次真实推理中从第 0 步到第 32 步发生的事。看懂它，你就理解了快慢两条通道是怎么配合的：

步数发生了什么模型调用
t = 0把指令 + 第一帧画面送进模型，生成 4 个动作（如 ↑↑←↑）调用一次
t = 1–3直接执行剩下 3 个动作，画面照常采集但不算不调用
t = 4新帧进来，复用前面的 KV 缓存，只 prefill 这一帧，再生成 4 个动作调用一次
t = 8, 12 … 28同上，缓存一直往后接，上下文越来越长但仍在窗口内每 4 步一次
t = 32窗口满了。从过去 32 步里均匀抽 8 帧当「记忆」，和当前帧一起重新送进模型，然后清空上下文，重新开始重建一次
t = 33 …重复上面的循环，但这次模型开头多了一段「你去过这些地方」的记忆每 4 步一次

对应代码：streamvln_agent.py 中 step() 的 run_model 分支与 reset_for_env 调用。

所以「32 步」和「8 帧」是两个不同尺度：32 是快窗口的长度（保证段内不算重复），8 是慢记忆的容量（保证跨段不失忆）。每 32 步，快窗口清零，但慢记忆把「这 32 步走到过哪」浓缩成 8 张图带进下一段。

为什么是 8 帧而不是 32 帧 论文的消融给了答案：把记忆从 2 帧加到 8 帧，成功率从 37.3 涨到 45.5；但继续加、或者干脆用全部历史，反而掉到 40.0。 记忆不是越多越好，8 帧左右是一个「够用且不干扰」的甜点。

07 / TRAINING这样一个模型，是怎么教出来的

7.1 起点：一个已经会看视频的模型

StreamVLN 没有从零训练。它的底座是 LLaVA-Video——一个把「视觉编码器」和「Qwen2-7B 语言模型」拼起来的多模态模型，已经见过大量视频和图文对，具备基本的时空理解能力。

研究团队做的事情，是把这个「会看视频、会聊天」的模型，改造成一个「会走路」的模型。改造方式是：把动作也当成语言，用导航数据继续训练它。

7.2 两阶段训练：先学会走，再学会不走偏

训练分两步，逻辑很像学车：

阶段喂什么数据目的
阶段一纯专家轨迹（oracle）告诉模型「标准答案长什么样」。1 个 epoch
阶段二专家轨迹 + DAgger 纠错 + 通用多模态数据告诉模型「走错了怎么救回来」，同时别忘了看图的通用本领。1 个 epoch

7.4 DAgger 是什么，为什么它值 240K 条数据

假设你只给模型看「完美司机的行车记录」。它学得很像，但一旦自己开的时候稍微偏了一点，它就从没见过这种局面——因为训练数据里从来没有「车身歪了 10 度」的画面。这叫分布偏移。

DAgger（Dataset Aggregation）的思路很直白：让学员自己开，教练坐旁边。学员开歪了，教练说「这时候应该往左打一点」，把这个「歪掉的状态 + 正确动作」记下来，加进训练集。反复几轮，模型就见过各种自己可能犯的错。

效果有多明显？消融实验里，去掉 DAgger 数据，R2R 的成功率直接掉 5.5 个点，SPL 掉 3.8 个点。这是所有单项里影响最大的之一。

08 / RESULTS成绩单：这些数字到底说明什么

8.1 五个指标，用打车来理解

假设你让司机送你到某个餐厅：

指标对应打车场景怎么算
NE最后停的位置离餐厅门口几米终点到目标的最短路径距离，单位米
OS路上有没有经过餐厅门口（但没停）轨迹上离目标最近的点 ≤ 3 米就算成功
SR最终有没有停在餐厅门口终点 ≤ 3 米算成功，看比例
SPL到了，而且没绕路SR 乘以「最短路 / 实际路」，绕路会打折
nDTW整条路线和导航推荐的像不像轨迹相似度，0 到 1

SR 和 SPL 永远一起看。一个 SR 很高但 SPL 很低的模型，说明它总能到，但是靠乱撞撞到的；一个 SPL 接近 SR 的模型，才是真的「知道路怎么走」。

8.3 消融实验：每个零件到底贡献多少

「消融」就是拆零件——把某个设计拿掉，看性能掉多少。这是判断一篇论文「哪里是真创新」最有效的方式。StreamVLN 的消融结果相当干净：

8.4 延迟：能不能真的上机器人

这是 StreamVLN 相比「纯刷榜」的论文最实在的地方——它敢报延迟。真机实验用的是宇树 Go2 机器狗，模型跑在一台带 RTX 4090 的远程服务器上，通过无线传输画面：

模型推理
0.27 秒 / 4 个动作（平均每个动作约 67 毫秒）
通信延迟
室内约 0.2 秒，室外约 1.0 秒
整体节奏
室内接近每秒 4 步，走起来是连续、不卡顿的

0.27 秒这个数字放在导航任务里意味着什么？人正常走路是每秒 1.4 米，机器人一步 25 厘米、4 步 1 米——也就是说，它「想 0.27 秒、走 1 秒」，脑子和腿是匹配的。

8.5 一个必须说清的数字问题

你如果去查资料，会看到两个不同的 R2R 成功率：56.9% 和 56.4%。这不是笔误，也不是造假，而是两个版本：

09 / CONTEXT它在整个领域里站在哪

要判断一个工作有没有意思，得看它前面的人卡在哪。

VLN 这个方向从 2018 年开始，大致走过了三代：

阶段代表做法核心思路卡在哪
第一代
2018–2022		 Seq2Seq、HAMT、ScaleVLN 专门为导航设计网络：视觉编码 + 语言编码 + 历史记忆模块 每个任务都要重训，泛化差
第二代
2023–2024		 NavGPT、MapGPT 把大模型当「大脑」，用文字描述场景，再让它规划 要把画面转成文字，信息损失大，延迟高
第三代
2024–2025		 NaVid、NaVILA、MapNav、StreamVLN 直接让视频大模型「看画面 → 出动作」，端到端 上下文怎么管、延迟怎么压

StreamVLN 属于第三代。它和几个最直接的同类相比，差别主要在「记忆怎么存」这一件事上：

方法记忆形式优点短板
NaVid 只看当前帧 + 极短历史 简单、快 长任务容易绕圈
NaVILA 高层出「走几米/转几度」，低层用强化学习执行 动作平滑，真机表现好 两层系统，调参复杂
MapNav 把历史画成一张带标注的语义地图 空间结构清晰，可解释 建图本身有误差，地图与画面对不齐
StreamVLN 流式对话（快）+ 3D 体素压缩（慢） 不用建图、不改模型、延迟恒定 记忆仍是固定容量，复杂空间会丢细节

一个有意思的对比：MapNav 选择「把记忆画出来」，StreamVLN 选择「把记忆压进 token 里」。 前者更接近人类的「认知地图」，后者更像人类「说不清但就是认得路」的直觉记忆。目前两条路都有人走，谁更好还没有定论。

10 / LIMITS诚实地看它的局限

论文不会主动告诉你它哪里不行。这一节是我读完论文和代码后，认为你该带着怀疑去看的几点。

10.1 「8 帧记忆」装不下复杂空间

8 帧，即使经过体素去重，信息量也是有限的。在一栋两层楼、十几个房间的房子里走十分钟，这 8 帧能保留多少？大概率只剩下几个模糊的「地标」。

论文里那些「超长时程」的演示（办公楼大堂、商场）确实能走完，但它们大多是路径清晰的单向路线，不需要「回到三楼那个房间拿东西」这种回溯能力。真正的长程任务，记忆仍是瓶颈。

10.2 体素剪枝依赖深度和位姿，而这两样在真机上很贵

在仿真里，深度图和相机位姿是白送的（Habitat 直接给真值）。真机上呢？深度要么靠双目/RGB-D 相机（室外阳光下经常失效），要么靠单目估计（有误差）；位姿要么靠轮式里程计（会漂），要么靠视觉 SLAM（要额外算力）。

误差一旦进入体素索引，就会出现「本来不是同一个格子，被误判成同一个」，把有用的 token 删掉。论文的真机实验用的是 Go2，配了深度相机，但公开代码里体素池化并没启用——这两件事放在一起看，说明工程落地还有距离。

10.3 每 32 步一次「重置」

这是代码层面的细节，但会影响真实体验：走到第 32、64、96 步时，上下文会被整体重建。重建的那一步，模型看到的输入结构和前一步完全不同（多了 8 张记忆图，少了一整段对话）。这可能造成个别时刻的动作抖动或判断突变。 论文的评测指标是整条轨迹的平均值，掩盖了这种瞬时异常。

10.4 动作空间是写死的

「前进 25 厘米、转 15 度」是 VLN-CE 的标准，但真实机器人底盘千差万别。轮式、四足、人形，步长和转弯半径都不一样。换一个平台，要么改动作定义重新训，要么在外面加一层转换——后者会引入误差累积。

10.5 评测仍以仿真为主

R2R-CE 和 RxR-CE 都是在 Matterport3D 扫描数据上做的，虽然逼真，但和真实世界的光照、反光、动态行人差距很大。论文的真机实验覆盖了客厅、卧室、办公区、商场、户外步道，场景挺全，但没有给出量化的真机成功率——只有定性描述和视频演示。

一句话总结局限 它解决的是「上下文和延迟」这个工程瓶颈，而不是「机器人真正理解空间」这个科学问题。 记忆被压缩到 8 帧，本质上是用一个固定预算去近似无限历史，预算之内很优雅，预算之外仍会失灵。

pip install -e habitat-lab
pip install -e habitat-baselines

第二步，下数据。需要两类东西：3D 场景（MP3D 约 90 个房子，或 HM3D）和 VLN-CE 的回合文件（episodes）。MP3D 需要申请授权，这一步会卡住不少人。

第三步，跑评测。仓库提供了一键脚本：

sh scripts/streamvln_eval_multi_gpu.sh

如果你想跳过仿真、只看模型怎么「看图说话」，可以直接用 Hugging Face 上的 transformers 接口加载权重，喂一张图 + 一句话，看它输出什么动作字符。这是理解「动作即文本」最直观的方式。

11.3 三条容易踩的坑

  • 数据版本要对齐。2025 年 9 月之后要用 R2R_VLNCE_v1-3，用旧版数据评测结果对不上。
  • num_history 必须传给模型。仓库更新日志里专门提过这个 bug：不传会默认 None，性能大幅下降。
  • 真机和仿真用不同权重。真机版去掉了指令里没提到的初始转向，还加强了避障——直接拿评测权重上机器人，会看到它开局先莫名其妙转两圈。

12 / GLOSSARY术语表：看不懂时回来查

术语人话解释
VLNVision-and-Language Navigation，视觉语言导航。跟着一句话在环境里找路。
VLN-CE连续环境版的 VLN。机器人真的在走，输出「前进/转向」这类底层动作，而不是在节点间瞬移。
Token模型处理的最小单位。文字里约等于一个字/词，图像里是一小块画面（patch）。
Patch图像被切成的固定大小方块，通常 14×14 像素。一帧图能切出一百多个。
Video-LLM能同时理解视频和文字的大模型。StreamVLN 用的 LLaVA-Video 就是。
Prefill预填充。模型把整段输入先「读一遍」并算好中间状态，是最耗时的阶段。
Decode解码。模型一个一个往外吐字，每吐一个都要查前面的缓存。
KV Cache把 prefill 算出的 Key/Value 存起来复用，避免重复计算。省时间但吃显存。
滑动窗口只保留最近 N 轮上下文，旧的移出去。保证长度恒定。
Token 剪枝从一堆 token 里挑一部分保留，其余丢掉。注意是「挑」不是「改」。
体素 / Voxel三维空间里的小立方格，相当于 3D 版的像素。
反投影用深度和相机参数，把 2D 图像上的点还原到 3D 空间中的位置。
DAgger一种训练技巧：让模型自己走，专家在旁边纠正错误，把纠正样本加入训练集。
Oracle 轨迹专家示范，也就是标准答案路径。不是「神谕」，就是人走的最优路线。
Action Chunking一次预测多个连续动作再一起执行，让动作更连贯、推理更省。
HabitatMeta 开源的室内仿真平台。VLN-CE 的标准测试环境。
Matterport3D / HM3D两套真实房屋的 3D 扫描数据集，分别是 90 个和上千个场景。
R2R / RxR两个导航指令数据集。R2R 短指令（约 29 词），RxR 长指令且多语言。
SR / SPL成功率 / 带路径加权的成功率。后者会惩罚绕路。
Egocentric第一人称视角。机器人看到的就是它自己眼睛看到的。
